# Dose Escalation Rules Checker for FACTS

> **Project Scope**: Build a deterministic validation engine for Phase I clinical trial dose-escalation models within the FACTS (Fixed and Adaptive Clinical Trial Simulator) ecosystem.

This project involves building a rule-checking validation engine designed to audit and verify simulation configurations for Phase I dose-escalation designs. The engine currently provides comprehensive rule validation for standard rule-based and interval-based designs, including **3+3**, **i3+3**, **BOIN**, **mTPI**, and **mTPI-2**. 

While quantifying total edge-case coverage across a massive simulation platform is inherently complex, the initial engine successfully met all core operational requirements for production use. Active development is now focused on expanding the engine to support the highly complex, non-deprecated **Continual Reassessment Method (CRM)** model, which introduces a significantly deeper layer of statistical mechanics.

---

## Technical Challenges

### 1. Bridging the Gap to Advanced Biostatistics
The primary hurdle of this project wasn't the syntax—it was mastering the underlying biostatistical frameworks. To build a rules engine that accurately catches configuration errors, I needed an airtight understanding of the mathematical constraints governing each design model. 

This required cross-referencing statistical literature, parsing domain-specific jargon, and establishing rigorous test suites. Because I was dealing with complex algorithms, I implemented a strict verification workflow: prototyping logic via LLMs, isolating variables, and validating outputs against established baseline simulations in FACTS. Having access to internal domain experts to verify core assumptions was invaluable throughout this deep dive into biostatistics.

### 2. Reverse-Engineering Undocumented Legacy Data
Another substantial architecture challenge lay in parsing the raw input data. FACTS provides its configuration data via raw text files, but lacked formal documentation for the underlying input variable schemas. 

To bypass this hurdle, I spent days manually manipulating the legacy software GUI, tracing state changes, and map-matching parameters back to the output files. Through this empirical reverse-engineering process, I successfully mapped out a comprehensive data dictionary containing **198 distinct variable definitions**. Managing this was further complicated by two decades of technical debt and non-intuitive legacy naming conventions. Fortunately, the downstream CSV files generated by the simulator were fully documented, allowing for cleaner integration on the data-ingestion side.

---

## System Architecture & Conclusion

The operational pipeline of the tool is cleanly decoupled into four core phases:
1. **Ingestion**: Multi-format parsers ingest raw configuration text files and simulation CSVs.
2. **Modeling**: Raw tokens are marshaled into structured, domain-specific object models representing the trial design constraints.
3. **Evaluation**: An extensive, modular rule-validation suite evaluates the objects for internal consistency and statistical boundary violations.
4. **Reporting**: The engine surfaces detailed telemetry on failed checks, preventing faulty simulation runs before they execute.

Navigating a massive simulation platform that has evolved over nearly 20 years was an intense exercise in managing legacy complexity. While reverse-engineering technical debt isn't always glamorous, the project was an incredible masterclass in domain-driven development and defensive programming.
